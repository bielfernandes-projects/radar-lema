## Anti-Patterns Verdict

**LLM assessment**: Zero sinais de AI slop. Nenhum gradient text, nenhuma eyebrow, nenhum ghost-card decorativo, nenhuma side-stripe border, nenhuma numbered section, nenhum glassmorphism, nenhum hero-metric. O UI é 100% MUI funcional — cards com conteúdo real, tipografia com hierarquia, ícones com propósito. Limpo, porém **genérico demais**. O `#1976d2` é literalmente a cor default do MUI `createTheme()`. Para um produto institucional que precisa transmitir confiança, parece "app interno feito em 2 dias" em vez de "ferramenta profissional da Lema".

**Deterministic scan**: Detector retornou exit code 0 — zero findings. Nenhum problema de contraste, slop patterns, ou violations detectadas.

## Overall Impression

App funcional e bem arquitetada, com progressive disclosure bem executado e filtros via URL params (compartilháveis). Porém sofre de três problemas estruturais: (1) EventFormPage é um muro de 500 linhas sem agrupamento visual; (2) tema MUI default transmite "ferramenta genérica" em vez de "produto institucional"; (3) falta proteção contra perda de dados em formulários complexos.

## What's Working

1. **Progressive disclosure bem executado**: Campos de endereço desaparecem para Online, preço só aparece quando não-gratuito, recorrência só expande quando toggle ativo. Isso reduz carga cognitiva de verdade. (`EventFormPage.jsx:388-448`)

2. **Filtros via URL params**: Filtros compartilháveis e bookmarkáveis — um detalhe profissional que respeita o workflow do usuário. O padrão se repete consistentemente em EventList, Favorites e PastEvents. (`EventFilters.jsx:27-38`)

3. **Arquitetura de componentes consistente**: EventCard + EventFilters reutilizados em 3 páginas de listagem. O usuário aprende um padrão e ele se repete — previsibilidade gera confiança.

## Priority Issues

### [P1] EventFormPage é um muro de 500 linhas sem agrupamento visual
**O que**: 9+ seções em scroll único, separadas apenas por `<Divider />`. Sem headers de seção, sem navegação por seção, sem sticky save.
**Por que importa**: Staff criando eventos complexos (com sessões, fotos, recorrência) enfrenta fadiga de decisão. No mobile, é um scroll infinito até o botão Salvar. Erros aparecem no topo mas o form não faz scroll.
**Fix**: Agrupar em `<Paper>` ou seções com `<Typography variant="h6">` como header. Considerar sticky "Salvar" no mobile. Adicionar âncora de seção ou accordion.
**Suggested command**: `$impeccable layout EventFormPage`

### [P1] Sem proteção de formulário sujo
**O que**: Navegar para fora do EventFormPage con cambios não salvos perde tudo sem aviso.
**Por que importa**: Staff preenchendo form complexo (sessões, fotos, recorrência) pode apertar "Voltar" ou clicar em nav link e perder tudo. É o cenário de máxima frustração para o power user.
**Fix**: Implementar `useBlocker` do react-router-dom ou `beforeunload`. Dialog de confirmação quando form está dirty.
**Suggested command**: `$impeccable harden EventFormPage`

### [P2] Busca escondida e inconsistente
**O que**: EventList tem busca atrás de IconButton + Popover. Favorites e PastEvents não têm busca.
**Por que importa**: Busca é ação primária para encontrar eventos, mas está disfarçada de botão de ícone. E sua ausência em Favorites/PastEvents impede busca dentro de eventos salvos.
**Fix**: TextField persistente no header de todas as listagens, ou pelo menos promover a busca para campo visível. Adicionar busca em Favorites e PastEvents.
**Suggested command**: `$impeccable layout EventList,Favorites,PastEvents`

### [P2] Sem feedback de sucesso após salvar evento
**O que**: Após criar/editar evento, redirect para `/gestao` sem confirmação.
**Por que importa**: Usuário não sabe se salvou com sucesso até ver o evento na lista. Viola "visibility of system status" no momento mais crítico.
**Fix**: Snackbar na página ManageEvents após redirect (via router state), ou Alert de sucesso no topo da lista.
**Suggested command**: `$impeccable polish EventFormPage,ManageEvents`

### [P3] "Remover todos" em Settings sem confirmação
**O que**: Botão "Remover todos" remove todos os lembretes de um evento instantaneamente, sem dialog de confirmação.
**Por que importa**: Ação destrutiva pode ser acionada acidentalmente. Diferente de delete de evento/categoria (que tem Dialog), remoção de lembretes é instantânea.
**Fix**: Adicionar Dialog de confirmação.
**Suggested command**: `$impeccable harden Settings`

## Persona Red Flags

### Alex (Power User / Staff)
- **ManageEvents sem busca, sem ordenação, sem paginação**: Todos eventos carregados de uma vez. Com 100+ eventos, fica inutil. Sem batch delete, sem edição inline — cada alteração exige navegar ao form completo.
- **Sem atalhos de teclado**: Não há como navegar rápido entre eventos ou ações comuns.

### Casey (Mobile User)
- **BottomNav com 6 itens para staff**: "Configurações" + "Categorias" empurram a barra para 6 ícones. Labels truncados a 0.65rem. Em telas pequenas, touch targets ficam apertados.
- **EventFormPage no mobile**: Form inteiro é um scroll longo sem sticky save. O botão Salvar só aparece no final — usuário precisa rolar tudo de volta depois de preencher.
- **SessionEditor no mobile**: 5 campos por sessão (data, hora, data, hora, delete) em Grid. Em telas xs, fica apertado mesmo com `size="small"`.

### Jordan (First-Timer)
- **Zero onboarding**: Primeiro login joga o usuário na EventList sem nenhuma indicação do que fazer.
- **Recorrência é obscura**: "Gerar sessões pela recorrência" — o que isso faz? O que acontece com sessões existentes? Sem helper text.
- **ReminderDialog aparece do nada**: Após favoritar, um dialog surge perguntando sobre lembretes. Para um primeiro usuário, é inesperado e inexplicado.

## Minor Observations

1. **Acentos faltando**: "Configuracoes", "Notificacoes", "Sessoes", "Acao" — todos sem acentos (ç, õ, é). Parece descuido para um produto institucional brasileiro.
2. **Sem skeleton loading**: Todos páginas usam CircularProgress centrado. Skeletons reduziriam percepção de espera.
3. **Placeholder image**: `/placeholder-event.png` — se não existir, broken image icons aparecem. Falta fallback inline.
4. **Navbar active state**: Só usa `fontWeight: 'bold'` — indicador muito sutil. Falta underline ou background.
5. **EventDetail back button**: Usa `window.history.back()` — se usuário veio de link externo, navega para fora do app.
6. **Sem 404 page**: Catch-all redireciona para `/login`. Link quebrado de evento manda usuário pro login, não para "evento não encontrado".
7. **Date inputs nativos**: Input type="date"/"time" tem UX inconsistente entre browsers (especialmente Safari).
8. **EventList sem scroll-to-top**: Mudar de página na paginação não faz scroll ao topo.
9. **Tema é MUI default**: `#1976d2` é a cor default do MUI. Zero identidade de marca para um produto que precisa parecer "institucional/confiável" sem parecer "ferramenta interna genérica".

## Questions to Consider

1. **MUI default theme transmite confiança institucional ou "app interno feito em 2 dias"?** O `#1976d2` é literalmente a primeira cor do `createTheme()`. Quanto effort para um tema custom que pareça Lema, não MUI demo?

2. **O que acontece quando a lista chegar a 500+ eventos?** Hoje tudo vem num fetch só (`fetchAllEventsWithMeta`). Tem plano para paginação server-side, infinite scroll, ou virtual scroll?

3. **Cliente RPPS e Staff Lema deveriam compartilhar a mesma nav?** Staff vê tudo (EventList + Favorites + PastEvents + ManageEvents + Categories + Settings). Staff precisa de um "management mode" separado, ou um toggle?

4. **BottomNav aguenta crescimento?** Com 6 itens hoje, o que acontece quando adicionar perfil, notificacoes, etc? Alguns itens deveriam ir para "Mais" ou para Settings?

5. **Qual a estratégia offline para um PWA?** Não há service worker visível, sem indicador offline, sem cache. Para um PWA que targets usuários em eventos (conectividade ruim), isso é uma lacuna.

6. **Por que a busca está escondida num popover no desktop?** No desktop há espaço de sobra para uma busca persistente. O popover adiciona fricção na ação mais comum.
